## Главный вывод

Это классическая причина, по которой контентно нормальный сайт не продвигается — проблема не в текстах, а в технической части.

## 🔴 КРИТИЧНО

### 1. Все внутренние ссылки ведут через двойной редирект (https → http → https)
**Где:** абсолютно все 36 страниц — ссылки вида `href="buhgalter.html"`, `href="blog-ii-v-razrabotke.html"` и т.д.
**Что происходит:** на сервере страницы физически лежат как `name.html`, но правило в `.htaccess` показывает их по "чистому" адресу `/name` и делает 301-редирект с `.html` на чистый адрес. Проверено на живом сайте:
```
https://umniy-site.ru/privacy.html  → 301 → http://umniy-site.ru/privacy   (откат на HTTP!)
http://umniy-site.ru/privacy        → 301 → https://umniy-site.ru/privacy (возврат на HTTPS)
```
То есть каждая ссылка внутри сайта сначала скидывает пользователя/Google-бота на незащищённый HTTP, а потом снова поднимает на HTTPS. Это происходит на **каждой** внутренней ссылке сайта, потому что все ссылки написаны с `.html`, хотя реальный (канонический) адрес страницы — без расширения.
**Почему критично:** два лишних редиректа на каждый переход — это прямой удар по скорости (Core Web Vitals / PageSpeed), по краулинговому бюджету Google (бот тратит лимит запросов на редиректы, а не на новый контент) и по консистентности сигналов (страница как бы "существует" по двум адресам одновременно).
**Что исправить:** во всех HTML-файлах заменить внутренние ссылки `href="название.html"` на `href="/название"` (без расширения), как уже сделано, например, для `href="https://umniy-site.ru/blog"` в `blog.html`.

### 2. sitemap.xml ссылается на 10 несуществующих страниц блога (гарантированные 404)
**Где:** `sitemap.xml`
**Что найдено:** в карте сайта перечислены адреса испаноязычных статей блога, для которых физически нет HTML-файлов:
```
/blog-necesita-restaurante-pagina-web
/blog-cuanto-cuesta-pagina-web-espana
/blog-inteligencia-artificial-diseno-web-pyme
/blog-web-salon-belleza-no-funciona
/blog-como-elegir-agencia-web-espana
/blog-seo-local-barcelona-negocio
/blog-academia-idiomas-como-conseguir-alumnos
/blog-web-inmobiliaria-rusia-espana
/blog-reservas-online-restaurante-espana
/blog-velocidad-web-afecta-ventas
```
Проверено на живом сайте — отдаёт 404. На эти адреса нет ни одной внутренней ссылки, то есть их никто не найдёт, кроме как через sitemap.
**Почему критично:** Google Search Console будет показывать ошибки обхода по sitemap, это снижает доверие к карте сайта в целом и тратит краулинговый бюджет на мёртвые адреса.
**Что исправить:** либо написать эти 10 статей (они явно запланированы — см. раздел "Конкуренты и запросы" ниже, это отдельный сегмент спроса), либо временно убрать их из `sitemap.xml` до публикации.

### 3. В sitemap.xml четыре адреса продублированы по 3 раза
**Где:** `sitemap.xml`
**Что найдено:**
```
/buhgalter-v-ispanii   — встречается 3 раза
/konsultant-v-ispanii  — встречается 3 раза
/psiholog-v-ispanii    — встречается 3 раза
/trener-v-ispanii      — встречается 3 раза
```
**Почему критично:** "грязная" карта сайта с дублями — ещё один сигнал низкого качества для поисковика, плюс путаница при анализе в Search Console.
**Что исправить:** оставить по одному вхождению каждого адреса.

### 4. Публично доступна страница-заглушка хостинга `index.php`
**Где:** файл `index.php`, живой адрес `https://umniy-site.ru/index.php` (ответ 200)
**Что найдено:** это стандартная заглушка Beget "Новый сайт успешно создан и готов к работе" с чужими скриптами (jQuery, fancybox, lodash с cdnjs) — не имеет отношения к реальному сайту. Сам домашний адрес `/` показывает правильный `index.html`, но `index.php` всё равно "висит" отдельным публичным адресом с мусорным содержанием.
**Почему критично:** если эта страница попадёт в индекс Google (а она доступна и технически индексируема — в `robots.txt` для неё нет запрета), она будет выглядеть как "сломанный" или заброшенный сайт прямо в поиске по бренду.
**Что исправить:** удалить файл с сервера (с вашего подтверждения) или на крайний случай закрыть его в `robots.txt`.

## 🟠 ВАЖНО

### 5. www и без-www отдают один и тот же контент без редиректа
**Где:** конфигурация сервера/хостинга
**Что найдено:**
```
https://umniy-site.ru      → 200 OK
https://www.umniy-site.ru  → 200 OK (идентичный контент, md5 совпадает)
```
Сервер не делает 301-редирект между версиями — обе версии домена одновременно "живые". Единственное, что сейчас спасает от дублирования в индексе — тег `<link rel="canonical" href="https://umniy-site.ru/...">`, который есть на всех страницах и указывает на версию без www.
**Почему важно:** canonical — это "рекомендация" для Google, а не жёсткое правило, он не всегда её соблюдает (особенно если на www-версию будут вести внешние ссылки). Правильная практика — сделать это явным 301-редиректом на уровне сервера.
**Что исправить:** настроить в панели Beget / `.htaccess` постоянный редирект `www.umniy-site.ru` → `umniy-site.ru` (301).

### 6. robots.txt запрещает несуществующий активный адрес
**Где:** `robots.txt` — строка `Disallow: /privacy.html`
**Что найдено:** реальная (каноническая) страница — `/privacy`, а `/privacy.html` — это промежуточный адрес, который редиректит на неё (см. проблему №1). Внутренняя ссылка на сайте (`href="privacy.html"` в `index.html`) ведёт именно на запрещённый для обхода адрес — то есть Google не может даже дойти до редиректа по этой ссылке с сайта.
**Что исправить:** после того как ссылки будут исправлены на чистые адреса (см. проблему №1), это правило станет неактуальным и его нужно будет убрать либо заменить на `Disallow: /privacy` — но сначала решите, нужно ли закрывать эту страницу от индексации вообще (обычно политику конфиденциальности от Google не скрывают).

### 7. У страницы privacy.html нет description и canonical
**Где:** `privacy.html`
**Что найдено:** в отличие от всех остальных 35 страниц, здесь нет `<meta name="description">` и `<link rel="canonical">`.
**Что исправить:** добавить оба тега для единообразия (даже у низкоприоритетной страницы).

### 8. Слишком длинные `<title>` почти на всех страницах
**Где:** большинство HTML-файлов
**Что найдено:** Google обычно показывает в выдаче заголовок длиной примерно до 55–60 символов (дальше обрезает по ширине). У сайта много заголовков длиной 70–90 символов, например:
```
blog-publikaciya-app-store-iz-rossii.html — 90 символов
blog-kak-proverit-seo-sajta.html — 85 символов
salon-krasoty-ispaniya.html — 82 символа
blog-pochemu-sajt-ne-indeksiruetsya.html — 82 символа
```
**Почему важно:** обрезанный в выдаче title теряет часть смысла и снижает CTR (кликабельность), а в некоторых случаях Google сам подменяет обрезанный title на свой вариант из текста страницы — то есть вы теряете контроль над тем, что видит пользователь в поиске.
**Что исправить:** сократить title до ~55–60 символов, оставив самое важное (конкретную услугу + локацию), убрать " — Forma Studio" там, где заголовок уже длинный (бренд можно оставить только на главной и ключевых страницах).

### 9. CSS не вынесен в отдельный файл — дублируется на каждой странице
**Где:** все HTML-файлы (встроенный `<style>` в `<head>`)
**Что найдено:** на страницах услуг инлайн-CSS занимает ~17 КБ, на страницах блога ~7–8 КБ — и это заново скачивается при каждом переходе на новую страницу, потому что стилей нет во внешнем файле, который браузер мог бы закэшировать один раз.
**Почему важно:** лишний вес каждой страницы и невозможность кэширования — это прямой минус к скорости загрузки, которая является фактором ранжирования Google (Core Web Vitals).
**Что исправить:** вынести общие стили в один файл `style.css`, подключаемый `<link rel="stylesheet">`, оставить инлайн только то, что действительно уникально для страницы.

### 10. Неоптимизированные изображения
**Где:** `kormybaby-seo.jpg`, `maria.jpg`, `alexandra.jpg`
**Что найдено:**
- `kormybaby-seo.jpg` — на самом деле это PNG-файл, просто сохранённый с расширением `.jpg` (404 КБ для скриншота — очень тяжело).
- `maria.jpg` (172 КБ, 768×1024) и `alexandra.jpg` (192 КБ, 1024×1024) — полноразмерные JPEG без сжатия для веба, без современных форматов (WebP/AVIF).
- Ни у одной из этих картинок не указаны атрибуты `width`/`height` → возможны сдвиги макета при загрузке (CLS).
**Что исправить:** пересохранить `kormybaby-seo.jpg` как настоящий сжатый JPEG или WebP, сжать фото людей (достаточно 400–600 px по широкой стороне для аватаров), добавить `width`/`height` в `<img>`.

### 11. Страница salon-krasoty-ispaniya.html заметно "тоньше" похожих страниц
**Где:** `salon-krasoty-ispaniya.html` — ~660 слов видимого текста
**Для сравнения:** `salon.html` ~1480 слов, `psiholog-v-ispanii.html` ~1610 слов, `trener-v-ispanii.html` ~1490 слов.
**Почему важно:** это коммерческая страница под конкурентный запрос ("салон красоты в Испании"), и такой разрыв в объёме контента по сравнению с остальными страницами того же типа говорит, что раздел недоработан — меньше шансов закрыть запрос пользователя и ранжироваться на уровне остальных нишевых страниц.
**Что исправить:** дополнить блоками, которые есть на остальных нишевых страницах (кейсы, процесс работы, FAQ, гарантии) — судя по структуре h2/h3, часть блоков просто отсутствует.

## 🟡 ЖЕЛАТЕЛЬНО

### 12. Нет микроразметки FAQPage для блока FAQ
На главной странице есть секция `id="faq"`, но она не размечена как `FAQPage` в JSON-LD. Сейчас используется только `ProfessionalService`, `Service`, `Offer`. Разметка FAQ даёт шанс на расширенный сниппет (раскрывающиеся вопросы прямо в выдаче Google).

### 13. Нет микроразметки для отзывов (Review / AggregateRating)
Есть секция `id="reviews"`, но без структурированных данных — это упущенная возможность для звёздочек рейтинга в сниппете.

### 14. Нет микроразметки Article/BlogPosting для статей блога
Ни один из 19 файлов `blog-*.html` не содержит `application/ld+json` — у статей блога нет структурированных данных (автор, дата публикации), хотя у страниц услуг разметка есть.

### 15. `loading="lazy"` используется только у одной из трёх реальных фотографий
У `maria.jpg` и `alexandra.jpg` атрибут отсутствует (хотя если фото показывается в самом начале экрана — это нормально, lazy там и не нужен; стоит просто перепроверить, какие изображения ниже первого экрана).

## Конкуренты и запросы

Судя по контенту, сайт закрывает **две связанные, но разные аудитории**:

1. **Малый бизнес в России** по нишам: бухгалтер, психолог, тренер, салон красоты — запросы вида «сайт для психолога под ключ», «сайт для бухгалтера с SEO».
2. **Русскоязычные предприниматели в Испании / Барселоне** — запросы вида «сайт для психолога на русском Барселона», «бухгалтер для русских Барселона».

Это видно и в title/description — они явно написаны под конкретные ключевые фразы, что хорошо.

**Найден третий, пока не реализованный сегмент:** судя по 10 "утерянным" адресам в sitemap (см. проблему №2), сайт изначально планировал статьи **на испанском языке** под запросы местных (не русскоязычных) предпринимателей: «cuanto cuesta pagina web España», «SEO local Barcelona negocio», «agencia web España» и т.д. Это отдельный рынок — конкуренция там идёт с испаноязычными веб-студиями, а не с русскоязычными. Сейчас на сайте **нет ни одной полностью испаноязычной страницы** — это нереализованная ниша роста, а не техническая проблема. Рекомендация: либо довести эти 10 статей до публикации (отдельный приток испаноязычного трафика), либо сознательно отложить и убрать мёртвые ссылки из sitemap, чтобы не портить техническое SEO прямо сейчас.

Также стоит проверить частотность и добавить вариации «веб-студия», «разработка сайта под ключ цена», «сайт с нуля для [ниша]» — сейчас упор сделан на «сайт для [профессия]», это сужает охват.

1. **Почистить sitemap.xml** — убрать 10 ссылок на несуществующие испаноязычные статьи и убрать дубли (`buhgalter-v-ispanii`, `konsultant-v-ispanii`, `psiholog-v-ispanii`, `trener-v-ispanii` — оставить по одному вхождению).

3. **Удалить или заблокировать `index.php`** — заглушка хостинга не должна быть публично доступна.
4. **Настроить 301-редирект с www на без-www** на уровне сервера (не только через canonical-тег).
5. **Пересмотреть robots.txt** — убрать/исправить правило `Disallow: /privacy.html` после исправления ссылок (шаг 2).

7. **Сократить длинные `<title>`** (сейчас 70–90 символов) до ~55–60 символов на страницах, где заголовок обрезается в выдаче.
8. **Вынести CSS в отдельный файл** `style.css` вместо дублирования инлайн-стилей на каждой странице.
9. **Оптимизировать изображения**: пересохранить `kormybaby-seo.jpg` (сейчас PNG под видом .jpg), сжать `maria.jpg`/`alexandra.jpg`, добавить `width`/`height`.
10. **Решить судьбу 10 испаноязычных статей**: либо написать и опубликовать (новый сегмент трафика), либо официально отложить и не держать мёртвые ссылки в sitemap.
